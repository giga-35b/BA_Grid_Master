# 匹配阶段与手机资源分析（2026-08-31）

## 结论

当前瓶颈不是推荐、主线程卡住或长期抢不到 CPU，而是**模板生成的计算与运行时开销**。工作线程的调用链样本中，`Source.render` 占 81.48%（含其调用），`compare` 占 8.01%；匹配子树整体占 89.58%。模板生成约占匹配子树样本的 91%。这些是用户态 CPU 采样比例，不是精确墙钟分段，不可将父子调用占比相加。

JIT 编译同样值得优先排查。每次识别附近，JIT 线程消耗约 2.1 秒 CPU；这与匹配线程并行，**不能再加到界面显示的约 3 秒上**。采样证实其中包含真实的 JIT 编译任务、编译内存管理及计时，不能将它简单说成首次预热。尚未做同代码、非 Debug 包的实机对照，因此不能将全部开销归因于 Debug 或断言 Release 能达到某个速度。

## CPU 调度与核心使用

通过 `/proc/<pid>/task/<tid>/schedstat` 取差值，区分真正运行与排队等待。字段定义来自 [Linux 内核文档](https://www.kernel.org/doc/html/latest/scheduler/sched-stats.html)。

| 线程 | 第一轮测试 1 CPU / 排队 | 第一轮测试 2 CPU / 排队 |
| --- | ---: | ---: |
| DefaultDispatch，TID 25709 | 2928 / 2.97 ms | 3086 / 5.47 ms |
| Jit thread pool，TID 25620 | 2085 / 94.01 ms | 2078 / 84.46 ms |
| HeapTaskDaemon，TID 25623 | 146 / 4.55 ms | 136 / 3.42 ms |

时间窗由结果日志反推匹配范围，并向外选取相邻资源快照，因此包含少量相邻阶段，不能与 `placementMs` 逐毫秒相等。线程字段是顺序读取，不是同时冻结快照；第一轮实际采样间隔中位数 0.877 秒，第二轮 0.752 秒，不声称达到了配置期望的 250ms 精度。

第二轮四个时间窗中，工作线程 CPU 约 2876–3176ms，排队 2.08–6.61ms；JIT CPU 2103–2164ms。其余两个 DefaultDispatch 工作线程几乎未运行，代码也确实串行执行匹配。

- 工作线程在计算期间实际允许的 CPU 始终为 `0-3`，cpuset 为 `/camera-daemon/limit-level2`。不是仅根据空闲截图推测。
- CPU 0–5 属于 policy0，硬件最大频率 3.5328GHz；CPU 6–7 属于 policy6，硬件最大频率 4.32GHz。不要把 CPU 0–3 随意称作“小核”。
- 计算期间 policy0 多数读数为 3.072–3.5328GHz，偶见 2.7456GHz；policy6 多数约 1.0176GHz。前者是核心组频率快照，不是每条指令的精确频率。
- 说明应用没有用到最高频的 6–7 核，但当前线程几乎持续得到 CPU，**不是因为排队等待损失数秒**。核心限制由谁触发、解除后会快多少，尚无因果对照。
- 不建议直接用 taskset、修改 cpuset 或强制最高性能模式解决。这会改变测试条件，也可能影响游戏和续航。

## 调用栈热点

使用手机自带 simpleperf 的应用内模式，不更改全局采样参数：

```text
run-as com.bagridmaster.app simpleperf record --in-app -p 5375
  -e cpu-clock:u -f 99 --call-graph dwarf,8192 --duration 180
  --size-limit 32M --user-buffer-size 8M -o cache/<本轮文件>
```

有效记录 1673 个样本，丢失 0。工具的 Android 应用采样能力及 Debug/Release 配置参考 [AOSP simpleperf 文档](https://android.googlesource.com/platform/system/extras/+show/main/simpleperf/doc/android_application_profiling.md)。

### 工作线程内的主要调用链（含子调用）

| 调用 | 工作线程样本占比 |
| --- | ---: |
| LocalTemplateMatcher.match | 89.58% |

渲染路径含大量双线性插值、舍入、像素访问、前景判断及亮度计算。样本也显示较多 JNI 跳板、JIT 入队/锁操作和未被内联的像素容器 getter。不能因为调用链上出现解释器祖先，就声称 97% 时间都在解释执行；多个热点函数的代码明确来自 `[JIT app cache]`。

JIT 线程的调用链包含 `JitCompileTask::Run`、`CompileMethodInternal`、`JitCompiler::CompileMethod`，以及分配/释放、TrimMaps 和计时。未取得逐方法编译次数，尚不能断言某个方法在无限重编译。

- CPU 计算时确有瞬时高温；不能说手机始终凉。记录中的 Thermal Status、对应温度状态仍为 0，CPU 冷却设备未报告节流，工作核心组频率也没有持续降至低频。现有证据不支持把约 3 秒主要归咎于热降频；仍不能排除厂商未通过此接口报告的电源策略。
- 应用 PSS 第二轮从约 146MiB 到 170MiB；SwapPss 从约 36MiB 降至 19MiB。不能仅看到 swap 已使用就断言正在严重换页。
- 第二轮匹配工作线程的大页故障（major faults）增量为 0/0/4/0，未见内存枯竭导致的持续换页证据。minor faults 较多并不等于磁盘 I/O。
- HeapTaskDaemon 有约 0.10–0.14 秒 CPU 工作，但不代表同等时长的 stop-the-world 暂停；当前证据不支持 GC 是秒级主因。

## 代码工作量与优化方向（本轮未实施）

1. **先做同代码非 Debug 对照。** 保持识别输入、设置、设备电源和工作流程一致，确认 ART/构建模式的份额。需要另行同意测试包安装，不能把未签名 Release 直接装上，也不能把调试签名叫作正式发布签名。
2. **优先减少模板生成，而不是先砍评分精度。** 当前为只露出 H2 的一格也生成完整 4×2 模板。可以按渲染参数合并多个摆法的工作，或只生成已观察格所需区域（必须保留插值/高斯滤波的边缘依赖），保持采样大小、候选搜索与阈值不变。
3. **检验缓存淘汰。** 4×2、每格32×32时，一张模板按现有缓存公式计费 131328 字节，8MiB 只容纳63张。单个摆法精调最多请求81组参数，多个摆法间可能淘汰后重复渲染。此处是静态推导，尚未加入命中/淘汰计数，不能当成已经测得的缓存命中率。
4. **核算工作量。** 此图 c 的合法摆放有横向4个、纵向4个。静态上限是3024次粗比较+5832次精比较，每次扫描已见格28×28内部像素；最多约694万次像素访问，732次渲染请求。比例不合格的渲染会被跳过，缓存也会复用，故不是实测执行次数。
5. **暂不盲目并行。** 当前一个匹配线程之外，JIT 已同时使用明显 CPU 资源；直接开多个匹配线程会扩大临时数组和缓存，可能提高温度、争用游戏资源。应先减少重复工作，再对有上限的并行做独立对照。
